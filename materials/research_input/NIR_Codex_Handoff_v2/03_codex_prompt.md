**Тема НИР:** «Методы обучения ансамблей деревьев решений, устойчивых к сдвигу распределения табличных данных».

## 1. Общая задача

**Полностью построить и использовать** воспроизводимый Python/R-стенд для оценки ансамблей деревьев при строгой multi-source, source-only Domain Generalization. Охватить четыре линии: RF-классификация, RF-регрессия, GBDT-классификация, GBDT-регрессия. Реализовать baselines и специализированные существующие алгоритмы, провести эксперименты, статистический анализ, получить CSV/Parquet результатов, научные таблицы, графики и черновой раздел НИР с выводами. **Собственный новый DG-алгоритм не изобретать.**

**Обязательное ядро для попытки полноценного воспроизведения:**
1. **IRF** — классификация и регрессия (оба режима присутствуют в оригинальной работе).
2. **Constrained Random Forest** — классификация.
3. **Meta-forests** — классификация, включая meta-train/meta-test, MMD и авторское взвешивание лесов. **Не пропускать из-за отсутствия готового кода: искать оригинал, сверять формулы, реализовывать воспроизводимую версию и проверять её.**
4. **MaxRM-RF** — регрессия; posthoc обязателен к попытке, остальные варианты при технической и научной возможности.
5. **Era Splitting / Directional Era Splitting** — прежде всего регрессия.
6. **Anchor Boosting** — регрессия и бинарная классификация, только source-only DG, без target refit.

Дополнительные самостоятельные кандидаты: Time Robust Forest (RF temporal classification), MixMax для XGBoost (пометить его исходную known-group постановку), Extra Trees, HistGBDT, XGBoost, LightGBM, CatBoost, при наличии ресурсов — корректно проверенные классификационные tree-DRO. Дополнительные подходы можно включать в исследования по обоснованному приоритету. Не превращать универсальные IRM/REx/Group DRO автоматически в «готовые RF/GBDT методы».

## 2. Степень автономности: высокая

**Не ограничивайся P0–P1 и не останавливайся для утверждения каждого шага.** Самостоятельно:
- проверяй актуальные ссылки, формулы, лицензии и реализации;
- скачивай открытые источники и пригодные наборы, создавай изолированные окружения Python/R;
- выбирай и документируй архитектуру, порядок работ, адаптеры и оптимизацию вычислений;
- устраняй технические несовместимости, добавляй тесты, делаешь авторизованную независимую реализацию по статье, если код отсутствует;
- при непригодном наборе выбирай научно обоснованную замену **без доступа к целевым данным**;
- запускай пилоты, проводи source-only HPO, фиксируй протокол и затем выполняй допустимые финальные target-тесты;
- продолжай до максимально полного отчёта, не прекращая работу только потому, что первый набор/алгоритм оказался сложным.

Изменяемые численные значения в YAML — **предложения**, не неприкосновенное ТЗ. Корректируй source-only решения на основании доступности данных, оригинальной математики и вычислительного бюджета. Все изменения — в журнале решений, с причиной и датой; до первого target inference заморозь финальную версию и её хеш.

Не требуй согласования на каждую замену библиотеки или refactor. **Обращайся к пользователю только при реальном внешнем блокере** (credentialed/proprietary данные, платные ресурсы, разрешения, неустранимое расхождение формул, невозможность обеспечить строгий DG и др.). Если часть задач заблокирована, делай остальные, фиксируй пробелы и не заявляй о полном выполнении без доказательств.

## 3. Непересекаемое ограничение: строгий DG

До `protocol_freeze`:
- запрещено извлекать `X`, `y`, статистики, признаки и метрики настоящих target domains;
- `source` и `target` должны быть логически/физически изолированы, а train/HPO API не должны возвращать target-объекты;
- предобработка в каждом source fold обучается только на train-source части; для временных задач train предшествует validation;
- число, состав доменов, preprocessing, метрики, гиперпараметрические сетки, ограничения бюджета и список планируемых target-тестов выбираются без знания целевого результата.

После `protocol_freeze` разрешена единственная **предзаданная серия** финальных target оценок для frozen методов/seeds/задач. Несколько заранее перечисленных запусков составляют одну серию; это не означает «одна модель на весь проект». **Не корректируй архитектуру/гиперпараметры по итоговым target-метрикам.** Любые ошибки после финала оформляй отдельным протоколом и учитывай предыдущие попытки; не маскируй повторные target evaluations под fresh holdout.

Это условие выше любой свободы исследователя. Ни одно улучшение чисел не оправдывает утечку target.

## 4. Исследовательские данные

**Начальный shortlist**, который требуется самостоятельно проверять: классификация — Folktables ACSIncome (штаты), TableShift Hospital Readmission, другие подходящие многодоменные TableShift; регрессия — Shifts Weather temperature, TabReD Cooking Time / Delivery ETA при наличии действительных исходных eras; резерв — Shifts Vessel Power, California Housing spatial domains, Numerai eras. Для Shifts Weather precipitation classification поддержка задачи и классов проверяется отдельно; не превращай multiclass в binary только для удобства. Не называй временное разбиение strict DG, если доступно только два IID-like набора без нескольких естественных source environments.

Выбери минимум две информативные задачи классификации и две регрессии при наличии фактических доступных данных и честного протокола. Для каждой задачи проверяй RF и GBDT baselines. Обязательные специализированные методы сравнивай с **парными baselines собственного движка**, где это технически возможно; различия движков не выдавай за эффект DG-штрафа.

Предпочти несколько **разных механизмов реального shift**, а не только дублирование набора данных под разными названиями. При необходимости добавь заранее описанную управляемую синтетику для проверки причинного механизма. Не объявляй чистый covariate/concept/label shift без математически или эмпирически обоснованного диагноза.

## 5. Алгоритмы — не просто import check

Для каждого из шести методов:
- получи и прочитай исходную публикацию + supplement; исследуй официальный и независимый код, статусы лицензий;
- выпиши точный objective, pseudocode, task support и гиперпараметры со ссылками на секции/формулы;
- реализуй или интегрируй метод, подготовь юнит-тесты механики и smoke fit/predict на source/synthetic;
- проверь ключевые инварианты и максимально достижимую репликацию чисел статьи (если есть доступ к данным);
- запусти на общих DG datasets, если task support корректен;
- если возникла непреодолимая неоднозначность, не выдавай приближённую интерпретацию за авторский алгоритм. Запиши альтернативы, выполни контролируемую ablation и поставь метку `independent_interpretation`, если это научно допустимо, иначе `blocked_unverified`.

**Специально для Meta-forests:** обязательно предприми самостоятельное воспроизведение полного ансамбля (не только RF baseline или MMD-диагностику). Раздели веса accuracy/MMD, маскирование признаков, количество лесов и правильное source-only meta-test. Контролируй бюджет относительно RF с тем же числом/совокупной стоимостью деревьев. Оригинальный target domain не может участвовать в meta-training либо настройке. Подробности в `06_method_reproduction.md`.

## 6. Выполни полный цикл без искусственной остановки

**P0 — аудит**: источники, версии, доступность данных/этикеток сред, лицензии, leakage, метрики и математика методов; работоспособность API.

**P1 — разработка и source-only пилоты**: пайплайн, baselines, специализированные алгоритмы, воспроизводимость, unit tests, source-domain CV и runtime. Все проблемные участки задокументируй.

**P2 — самостоятельное замораживание протокола**: на основании source-only диагностики, реального железа и методов, которые удалось корректно реализовать, зафиксируй final datasets, target IDs (выбраны до чтения target), feature schema, metrics, HPO, seeds, split logic, список опытов, stopping criteria, хеши конфигурации и кода; отчёт `preregistration.md` и `frozen_protocol.json`.

**P3 — финальные эксперименты**: только после P2, с source-only selection, затем одна frozen target evaluation series. Логируй и храни исходные предсказания и метрики, время/память, per-domain результаты. Проверь соответствие запретам target leakage.

**P4 — научный разбор**: сравнение с paired baselines; статистическая неопределённость; влияние числа доменов, параметров и типа shift; нулевые и отрицательные результаты. Сгенерируй таблицы, графики и черновик «Методика экспериментов — Результаты — Обсуждение — Ограничения», честно разделяя собственные измерения и опубликованные числа.

**Не останавливайся после P1 с одними TODO, если дальнейшие этапы доступны.** Если технические этапы длительны, продолжай по ходу текущей работы и фиксируй реальные артефакты. Не обещай асинхронное исполнение, если режим не позволяет: верни максимальный фактический результат и точные команды продолжения.

## 7. Артефакты и критерии оценки

Создай рабочий репозиторий с CLI и тестами, конфигами, документацией, source/target data guards, логами seed/version/commit, auditable HPO, freeze/target unlock. Отчётные outputs перечислены в `07_outputs_and_quality.md`. Обязательно `method_matrix.csv` для всех шести с `exact_replication / independent_reimplementation / independent_interpretation / blocked` и причина. Отдельно укажи, сколько методов реально обучено и на каких доменах, какие остались блокированы, какие результаты собственные.

**Готовый результат** — это реальный работающий код + выполненные допустимые эксперименты + честные результатные файлы и научно интерпретируемые графики. Если не всё достижимо из-за вычислений/доступа/формул, выполни остальное и выдай точный отчёт, а не притворяйся, что всё проверено.

Начинай с чтения пакета и самостоятельного выполнения. Не задавай предварительных вопросов, ответы на которые можно получить из файлов, открытых первоисточников и source-only аудита.
