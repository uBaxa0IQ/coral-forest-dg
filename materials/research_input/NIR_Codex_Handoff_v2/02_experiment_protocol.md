# НИР — автономная спецификация сравнительных экспериментов DG (проект v2.0)

**Срез:** 04.11.2026. **Статус:** проект методики, не экспериментальные результаты. **Назначение:** научные границы для максимально автономной работы Codex от независимой проверки методов и данных до воспроизводимых финальных сравнений. Codex вправе корректировать проектные детали по фактам P0/P1 и самостоятельно заморозить P2 ДО любого доступа к target. Исторические сведения из обзоров требуют проверки по оригиналам.

## 1. Исследовательская цель

Тема НИР: **«Методы обучения ансамблей деревьев решений, устойчивых к сдвигу распределения табличных данных»**.

Цель экспериментальной части — **независимо сравнить существующие методы RF и GBDT** в классификации и регрессии при изменении естественных или контролируемых сред, исследовать влияние механизма робастности, процедуры выбора гиперпараметров, состава исходных доменов и вычислительной стоимости. Не разрабатывать новый метод. **Нет гипотезы об обязательном выигрыше DG-методов:** отрицательный результат тоже научно содержателен.

Постановка: *multi-source, source-only Domain Generalization* (DG). Даны размеченные среды `E_source = {e_1,...,e_k}`; в них разрешено обучать модель и выбирать гиперпараметры через внутреннее исключение исходных сред. Целевые среды `E_target` не участвуют ни в обучении, ни в вычислении статистик преобразований, ни в подборе моделей/датасетов/процедур. Целевые `X` и `y` можно открыть лишь для **однократного финального оценивания зафиксированных конфигураций**. Метки принадлежности исходным средам доступны методам; метки целевых сред используются лишь для отчёта после разморозки.

## 2. Масштаб и критерий завершения

**Четыре обязательные исследовательские линии:** RF-классификация, RF-регрессия, GBDT-классификация, GBDT-регрессия. Это не означает принудительной реализации всех методов на всех наборах: отдельный метод участвует там, где опубликована/подтверждена поддержка соответствующей задачи и соблюден строгий протокол.

Ориентир минимальной основной программы: не менее **двух содержательно различных задач классификации** и **двух задач регрессии** после аудита данных; в каждой задаче обе стандартные модельные семьи (RF, GBDT), при наличии реализуемого DG-метода соответствующей семьи — сравнение его с парным baseline. Дополнительно как минимум **один заранее заданный синтетический сценарий** с известным генеративным механизмом (если это оправдано после базового этапа). Не выдавать разные датасеты из одного источника за полностью независимые исследования сдвига.

**Обязательное ядро попытки воспроизведения:** шесть самостоятельных методов — **IRF (classification/regression), CRF, Meta-forests, MaxRM-RF, Era Splitting, Anchor Boosting (classification/regression)**. **Meta-forests не резерв, а обязательная полноценная попытка реализации**, даже если авторский исходный код отсутствует. Успех не объявлять до выполнения математических и программных проверок; непреодолимые блокеры документировать. Дополнительные Time Robust Forest, MixMax и другие подходы — по доказанной полезности и ресурсам.

**Условие научной состоятельности:** протокол и выбор данных зафиксированы до чтения любых целевых метрик; опубликованы результаты всех запланированных методов/задач, в том числе нулевые и отрицательные. Если некоторые методы технически недоступны, они остаются в литературном разделе, но не изображаются как экспериментально проверенные.

**Что уточнено по первоисточникам:** официальный Shifts Weather — 10 млн записей, 123 метеопризнака, климато-временные метаданные, **обе задачи**: температура и класс осадков (https://shifts.ai/dataset). Официальный TabReD даёт `x_meta.npy`, `y.npy` и индексы `splits/default/{train,val,test}.npy`, но **существование достаточно подробных исходных эр только из списка файлов не следует** (https://github.com/yandex-research/tabred). TableShift Hospital Readmission использует 21 значение `admission source` и канонически исключает «emergency room» (https://tableshift.org/datasets.html).

### 3.1. Конкретный предложенный сплит для `C_ACS`

Использовать **ACSIncome, ACS PUMS 2018, `1-Year`, person** (этот пример официально поддержан Folktables). Внести в `config` до скачивания/открытия test:

- Предложенные source states: `CA, TX, NY, FL, IL, WA, GA, AZ`.
- Предложенные target states: `CO, NC, MA`.
- Домены = штаты, а не случайные подвыборки. Этот перечень **наша предварительная пререгистрация**, а не официальный benchmark split и не результат оценки target.
- Не включать ID штата в предикторы; `state` хранить как `environment_id` вне матрицы `X`. Все другие predictor columns — строго по официальной задаче ACSIncome; исключить целевую переменную и прямые утечки.
- Источник меток/трансформаций версии Folktables зафиксировать; возможные категориальные кодировки и missing values проверять **на source-only**. Сэмплирование при нехватке ресурсов только по заранее фиксированному числу на source domain/seed до обучения, без просмотра target.
- До P2 разрешены **документированные самостоятельные изменения** этого предложенного split по проверяемым причинам доступности, естественности доменов, представительности source и вычислительного бюджета; решение нельзя принимать по target features, labels или метрикам. Финальное решение и список альтернатив фиксировать до первого target-доступа.

### 3.2. Конкретный канонический target для `C_READM`

Использовать официальный идентификатор `diabetes_readmission`; source environment = остальные категории admission source, target = `emergency room` согласно документации TableShift. Строго исключить `admission source` из predictor columns по умолчанию (она используется как метка среды). **Проверить** метки категорий, класс-баланс по исходным группам, число слишком малых доменов, вероятность пересечения пациентов и схему уже выполненной предобработки. Непригодные маленькие source groups допускается исключать/объединять **только по правилу, принятому на source data до финального теста** и с записью причин; недопустимо создавать «псевдодомены» случайными folds.

### 3.3. Протокол `R_SHIFTS`

Предпочтение — **официальное разделение Shifts Weather**: train/in-domain development как источник исходных наблюдений (только те его части, чья роль заранее зафиксирована), shifted eval как закрытая цель. Для формирования source environments использовать доступные **в исходном train** `climate_type × calendar-period` или другой предопределённый внешний фактор. Временные блоки задавать естественными календарными интервалами, не квантили по целевым значениям. Фактическую схему принять лишь после аудита source timestamps/counts; желательно минимум 4 последовательные эпохи с несколькими климатами и достаточными наблюдениями. Не использовать `dev_out`, `eval_out` или целевые климатические статистики для HPO.

Учитывать: канонический сдвиг **смешанный климато-временной**, а не «чистый covariate shift». Для временной валидации держать хронологию; если климатическое исключение и временное моделирование конфликтуют, заранее выбрать **основную** (хронологическую) и **дополнительную** (leave-one-climate-source-out) валидационные оценки, не выбирать победителя по test.

### 3.4. Протокол `R_COOK` / `R_ETA`

Начать с изучения `info.json`, `x_meta.npy`, схемы признаков и `default/train` **без чтения `default/test`**. Удостовериться, что есть восстанавливаемая дата/этап, корректная монотонная временная ось и минимум 4 непересекающихся исходных естественных eras, причём source-обучение DG-метода в каждом pseudo-target fold сохраняет не менее двух train eras. Если `x_meta` не обеспечивает восстановление реальных временных сред, задачу **не объявлять полноценной temporal DG**: исключить из ядра или использовать лишь как temporal OOD baseline со специальной маркировкой.

**Замечание о готовой предобработке TabReD:** наличие скачиваемых `x_num/x_cat` не доказывает, что все операции были обучены без учёта target. Аудировать данные/скрипты preprocessing; если используется глобальная data-dependent обработка, перейти к исходным данным или пометить нарушение и не включать в strict DG основные выводы.

## 4. Модели и уровни обязательности

| Направление | Обязательная базовая модель | Специализированный метод | Готовность / оговорка |
|---|---|---|---|
| RF–classification | `RandomForestClassifier` + `ExtraTreesClassifier` | IRF-classification | **Обязательный кандидат**, точная реализация/формулы под аудит и, возможно, реализацию по первоисточнику. |
| RF–classification | RF, парный RF, если требуется | Constrained RF | **Обязательная попытка**, включая проверку авторского R-кода; при недоступности — независимая реализация по статье со статусом достоверности. |
| RF–classification | RF | Time Robust Forest | **Приоритет 1 для temporal datasets**, не переносить автоматически temporal evidence на все виды сдвигов. |
| RF–classification | RF / ансамбль RF с контролем числа деревьев | Meta-forests | **ОБЯЗАТЕЛЬНО воспроизвести или доказательно зафиксировать блокер**; проверка оригинальной meta-процедуры/MMD/весов и независимая реализация при отсутствии кода (см. 06_method_reproduction.md). |
| RF–regression | `RandomForestRegressor` | IRF-regression | **Обязательный кандидат**, математически описан в оригинальной статье; исполнимость не доказана. |
| RF–regression | RF в том же движке (`adaXT`) | MaxRM-RF (сначала `posthoc`, затем `local/global`) | **Обязательная попытка**, включая posthoc и проверку авторского кода; прочие варианты после математической проверки и оценки стоимости. |
| GBDT–classification | LightGBM baseline + XGBoost/CatBoost как внешние baselines | Anchor Boosting binary | **Обязательная попытка**, только source-only DG; gamma=1 — контрольный режим после проверки эквивалентности. |
| GBDT–classification | XGBoost | MixMax XGBoost | **Дополнительный метод**, исходно worst-group; собственная source-only DG-проверка обязательна. |
| GBDT–regression | `HistGradientBoostingRegressor`/парный `erasplit` baseline, LightGBM | Era Splitting, Directional Era Splitting | **Обязательная попытка**, документированный регрессионный API; базовый режим проверить по конкретной версии. |
| GBDT–regression | LightGBM paired baseline | Anchor Boosting regression | **Обязательная попытка**, в DG-протоколе; якоря только исходных сред, без target-refit. |

**Не считать готовыми для регрессии:** tree-варианты KL/CVaR/χ²-DRO без проверки соответствия градиентов квадратичной потере; опубликованный отчёт обнаружил расхождение между API и фактической формулой. DIRF/O-/HO-IRF оставить в литературной карте до появления доступного первоисточника/точного кода. Не пытаться «заполнить» GBDT-classification методом Era Splitting через неописанный classifier API.

**Ожидаемый результат для каждого из четырёх направлений** — baseline на соответствующих данных и максимально полный набор честно воспроизведённых применимых специализированных кандидатов. Все шесть центральных методов должны получить реальную попытку интеграции/реализации и итоговый статус; нельзя молча отложить Meta-forests или IRF. Если точное воспроизведение недостижимо, записать попытки, недостающие формулы, валидированные частичные компоненты и последствия для выводов, не подменяя метод случайной модификацией.

## 5. Парные baselines и честность сравнения

1. Для каждой модификации в идеале сохранить **тот же программный движок** и выключить DG-специфический компонент: `Era` ↔ штатный criterion того же fork, `Anchor` ↔ `gamma=1`/стандартный LightGBM, `MaxRM` ↔ исходный RF в `adaXT`; подтверждать эквивалентность по исходному коду и на smoke-тесте. Не прописывать неподтверждённые значения API в основной эксперимент.
2. Отдельно оценить сильный внешний baseline: scikit-learn RF/Extra Trees; XGBoost, LightGBM, CatBoost — **по уместности задачи и доступным ресурсам**, не обязательно все в пилоте.
3. Междвижковое сравнение (`Era` vs `Anchor`) отражает **практические модели в целом**, не чистый вклад регуляризатора; при анализе механизмов использовать **разницу относительно парного baseline**, затем сопоставлять эти разницы на одинаковых split.
4. Для **обязательного Meta-forests** воспроизвести полный meta-training → meta-validation source-only → MMD → weighting → aggregation; отдельно проверять маскирование и гиперпараметры; число лесов/деревьев и бюджет HPO фиксировать; сравнить с RF одинакового суммарного размера/затрат. Полное техническое ТЗ в `06_method_reproduction.md`.
5. Нельзя утверждать «превосходит» на основании разных датасетов/протоколов и чисел из разных статей.

## 6. Разбиения, source-only selection и противодействие leakage

### 6.1. Обычные невременные среды (ACS, Readmission)

- Сформировать набор исходных естественных доменов `S` и заранее закрытый target `T`.
- Для каждого кандидата HPO на заданном seed, по методу *leave-one-source-domain-out* (LOSO/LOEO): обучить на `S \ {e}`, оценить на `e`, повторить по заранее выбранным source доменам; **в момент обучения на `S \ {e}` не использовать объекты, метки, частоты и статистики `e` даже в трансформациях**.
- Изначально у метода может быть минимум 2 исходные среды; поэтому для LOSO желательно `|S| >= 3`, а сложные meta-алгоритмы могут требовать ещё больше. Если минимум нарушен — метод/fold несовместим, не считать это нулевой точностью.
- Сводить валидационные метрики **макроусреднением по pseudo-target source domains** (каждая среда имеет одинаковый вес). Основной критерий выбора заранее один на задачу.
- После HPO переобучить на **всех исходных доменах**, заморозить модель, преобразования и конфигурации; target передать отдельному evaluation entrypoint.

### 6.2. Временные среды (Weather, TabReD)

- Не применять симметричный LOSO, если обучение на более поздних source eras могло бы «подсказывать» раннему pseudo-target будущее.
- Использовать **rolling-origin / forward-chaining source validation**: для pseudo-target era `j` обучать лишь на `1..j-1`; первые эпохи использовать как warmup, пока не накопится число сред, необходимое DG-алгоритму. Расписание и вес pseudo-target folds фиксируются до просмотра результатов.
- Source meta: календарные границы задаются до теста; **никогда не выбирать число/размер eras по целевому RMSE**. Отдельный source-only эксперимент чувствительности `k_source` допускается только если заранее указан.
- Идеальный early stopping: оценивать число итераций через source rolling validation; после выбора заново обучать на полном source pool с фиксированным числом деревьев. Не применять target-dev/target-test ни для ранней остановки, ни для gamma/alpha.

### 6.3. Меры защиты

- **Логический/физический барьер:** `train` и `validate` читают только source; модуль `evaluate_target` после записи `frozen_protocol.json`, checksum и lock-флага. Отдельный режим/каталог с доступом к target только во время финальной оценки. Не использовать target даже для оценки количества классов, пропусков, imputation statistics, категорий, scale и feature selection.
- Разрешено заранее знать **идентификаторы** целевых доменов/официальные правила split — для пререгистрации; нельзя читать целевые записи/признаки/исходы для настройки.
- Каждый transformer (`imputer`, `encoder`, `scaler`, selection) переобучается **внутри конкретного source-training fold**. Для финальной модели — на полном source pool. Кодированные `unknown` категории в тесте обрабатываются заранее определённым правилом. Нельзя заполнять NaN средним по pooled source+target.
- Метку среды хранить в отдельном `e`, но не в `X` по умолчанию. Алгоритмы, которым нужны `e` или anchor `Z`, получают их через адаптер только при `fit` на source. Target не передавать в training adapter.
- Аудит идентификаторов: повторные пациенты, ученики/учебные сессии, регионы, дубликаты train/target, признаки, сформированные с будущими событиями. Если возможны пересечения — заранее определить group/entity holdout и задокументировать.
- Никакой ручной смены dataset shortlist, targets, seed, HPO grids или основных метрик после просмотра target scores. Исправление обнаруженного бага — версия нового протокола с записью причин, все результаты после фиксации показывать; тест на target не использовать циклически как validation.

## 7. Метрики и агрегирование

**Бинарная классификация:** primary `AUROC` (на каждой target-среде должны присутствовать оба класса; иначе `AUROC=NA`, без молчаливой замены метрики). Secondary: `log_loss`, `balanced_accuracy`, `accuracy`, `F1`/`AUPRC` при дисбалансе с явной prevalence. Вероятности для log loss — из штатного `predict_proba` или документированного интерфейса; порог для accuracy/F1 зафиксировать на source и не подбирать по target.

**Регрессия:** primary `RMSE`, secondary `MAE`, `MSE`, `R²` при корректном определении. В сравнении разных датасетов использовать при необходимости `normalized_RMSE`, где масштаб — `std(y)` **на исходном обучении**, а не на target. Не сравнивать напрямую абсолютные RMSE несоизмеримых целевых переменных.

**Domain aggregation:** каждая target-среда первично получает свою метрику. Для класса `macro AUROC` — среднее по целевым доменам с валидной AUROC (с указанием пропусков), `worst AUROC` — минимум; для регрессии `macro RMSE` и `worst RMSE` — максимум. `micro`/pooled метрики — только дополнительные, потому что большой домен не должен скрывать провал на маленьком.

**Статистика:** пилот — 3 заранее фиксированных seed `[11,23,47]`, финальная серия — предпочтительно 5 `[11,23,47,59,83]`, если технический бюджет позволяет (изменение числа до test lock!). Сообщать покомпонентные paired differences по одному target domain и seed; интервалы неопределённости по независимым доменам там, где их достаточно. Повторы случайного алгоритма на одном и том же target **не являются независимыми новыми доменами**; нельзя выдавать 5 seeds × 3 target за 15 независимых смен распределения. Если target один, worst-target метрика не является информативной отдельной статистикой.

**Стоимость:** `fit_wall_time_s`, `predict_wall_time_s`, peak RSS/память, число деревьев, HPO-compute отдельно. Сопоставлять машины/окружения и потоки; измерения времени имеют смысл только при контролируемой конфигурации CPU/RAM.

## 8. Гиперпараметры и вычислительный бюджет

- Сначала **pilot только на source**: до 8 HPO-кандидатов на метод и датасет, 3 seeds, не более 3–4 заранее назначенных pseudo-target folds; small source subset по предварительному правилу. Обучение на target отсутствует. Это оценка работоспособности и грубой стоимости, не финальный научный результат.
- Перед финальным target: бюджет зафиксировать в `experiment_config.yaml` по реальному CPU/RAM; ориентир **до 20 trial configurations на метод/датасет**, при сопоставимом бюджете парного baseline, 5 seeds если реально выполнимо. Это **предложение, а не утверждение о достаточности**.
- Каждый метод имеет обоснованную опубликованную/документированную сетку, а не случайно одинаковые гиперпараметры. Выбор производится **только по source-validation aggregate**; бюджет и effective compute выводить отдельно.
- Для RF сохранять число деревьев/`max_depth`/`min_samples_leaf` как контроль мощности; для GBDT learning rate, rounds, max_leaf_nodes, early stopping, regularization. Специфичные lambda/gamma/alpha проверять в коде и оригинальной статье.

## 9. Варианты экспериментов

**E0 (обязательно):** обычные RF/GBDT и paired non-DG baselines на доступных наборах, с полностью source-only HPO. Цель: сильный контроль, пригодность данных, карта неоднородности.

**E1 (ядро, обязательные попытки):** четыре направления и **все шесть основных методов** при их подтверждённой поддержке задачи. RF-classification — IRF + CRF + **Meta-forests** (Time Robust Forest дополнительно для temporal domains); RF-regression — IRF + MaxRM; GBDT-classification — Anchor binary (MixMax как смежное дополнение); GBDT-regression — Era + Directional Era + Anchor. Сравнение с paired baselines на общих splits, фиксированных метриках и сопоставимом HPO budget. Непригодный/неверифицируемый метод получает `blocked_unverified` с доказательством, но **не исчезает из плана незаметно**.

**E2 (планируемое расширение):** варьирование количества исходных сред, дисбаланса источников и силы штрафа; каждый фактор изменять на исходной части по предрегистрации, не по победителям на target. Контролировать общее число объектов при изменении числа сред, иначе смешиваются эффекты объёма данных и количества доменов.

**E3 (дополнение, не вместо реальных задач):** синтетика с известными структурными уравнениями: чистое изменение `P(X)` при фиксированном `P(Y|X)`; изменение силы ложной корреляции; сдвиг условной зависимости; гетероскедастический шум. Отдельные генераторы для классификации и регрессии. Утверждать чистый тип сдвига только по проверяемому механизму генератора.

## 11. Артефакты воспроизводимости

Каждый прогон сохраняет: dataset version/checksum и лицензия; индексы source/target (хеш и правила); численности и классы **только source** до финала; feature schema; fingerprints preprocessing; версии Python/R и пакетов; git commit; параметры и seeds; source folds; полный журнал HPO; размеры/время; source и final метрики в **разных файлах**; ошибки/исключения и причины исключения методов. Данные из защищённых источников не коммитить. Репликация строится из конфигов и необработанных источников с соблюдением лицензий.

## 12. Условия переходов — gate review

**P0: Data/method audit, без научных target-оценок.** Открыть только source-части и метаданные схемы; проверить лицензии, структуру `x_meta`, достаточное число environments, классы, временную последовательность, идентификаторы субъектов, объём RAM. Для алгоритмов — установить зависимости, сделать игрушечный `fit/predict` на **синтетике**, проверить baseline mode, support tasks, начальную воспроизводимость. Протокол не переходит к финалу при недоступных исходных средах/подозрении на leakage.

**P1: Пилот на source.** Обучить стандартные модели, прогнать source-CV, проверить runtime и правильность метрик/логов, сделать smoke-тест DG-реализаций на настоящих **source** данных. До P2 target не читается вообще.

**P2: Самостоятельная пререгистрация/заморозка Codex.** После завершения source-only проверок, без обязательного запроса пользовательского утверждения (кроме реальных внешних блокеров), зафиксировать перечень датасетов и исключённых целевых доменов, feature lists, ерas, правила исключения малых доменов, метрики, методы, HPO budget/grids, seeds, модели, способ агрегирования и сравнения, hash code/config. Создать `frozen_protocol.json` и подписанный лог; **все** последующие отклонения логировать.

**P3: Финальные эксперименты — выполнять автоматически при пройденных P0–P2 и доступных ресурсах.** Source-only подбор для каждой модели, переобучение на sources, затем **единственный финальный target evaluation для зафиксированных моделей/seed**. Результаты не используют для следующей итерации настройки. Если исправляется ошибка, оформить новый run/version, сохранить прежние оценки, показать отличие.

**P4: Анализ и отчёт.** Таблицы per-domain и макро, paired differences, стоимость, чувствительность и статистическая неопределённость; отдельно научные ограничения, предупреждения и воспроизводимость. В отчёте НИР включить методики/результаты/графики; код — ссылка на репозиторий или приложение (если допустимо), не обязательно полный листинг.

## 13. Границы самостоятельности Codex

**Можно самостоятельно:** искать и проверять новые первоисточники, исправлять неверные библиографические сведения, разрабатывать адаптеры/воспроизводимые реализации, выбирать более подходящие datasets и подтверждённые source environments, уменьшать объём source data, менять архитектуру и бюджеты HPO, проводить дополнительные проверяемые абляции — при условии, что решения до target зафиксированы с причиной. **Не нужен обязательный ручной approval P2.**

**Нельзя:** выбирать target states/periods по их признакам/метрикам; выдавать TabReD metadata за проверенные eras; приписывать неподтверждённые regressor/classifier режимы; «чинить» оригинальную формулу незаметно; использовать target для настройки, отладки, выбора методов/датасетов; менять классификационную задачу в регрессию ради совместимости; утверждать результаты до реального запуска.

**Внешние блокеры:** не обходить paywall, credential access, лицензионные ограничения; не задействовать платные ресурсы или чувствительные данные без разрешения. Если один опыт заблокирован, продолжать независимые разрешённые ветви и сформировать отчёт блокеров. Не гарантировать успешность всех шести алгоритмов заранее.

## 14. Открытые решения, которые должен проверить Codex в P0

1. Есть ли *реально доступные* `C_ACS`, `C_READM`, `R_SHIFTS`, `R_COOK`? Версии/лицензии/размеры source (без обращения к target).
2. Есть ли в `R_COOK/R_ETA` надёжный timestamp; сколько **естественных source eras** допустимо? Если нет — резервный план только на проверенных Shifts / иной регрессионной задаче.
3. Какие алгоритмы действительно исполняются: IRF (классификация и регрессия), CRF (R), TRF, MaxRM, Era, Anchor, Meta? Что нужно реализовать по статье и сколько труда?
4. Сопоставимы ли paired baselines на каждом программном движке?
5. Какие источники/преобразования содержат изначальный target leakage, и какие данные необходимо перегрузить из raw?
6. Какая оценка CPU/RAM/времени на source pilot, и какой финальный budget возможен?

**Итог:** Кодекс получает полномочия самостоятельно довести НИР через P0→P1→P2→P3→P4, не останавливаясь искусственно на пилоте. Условие перехода — проверенная научная/техническая корректность и источнико-ориентированная защита target, а не обязательное ручное одобрение каждого промежуточного решения. См. `03_codex_prompt.md`, `06_method_reproduction.md` и `07_outputs_and_quality.md`.
